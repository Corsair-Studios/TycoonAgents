Adding Other AIs: Agents, Routing & Fallback

Beyond one vendor
Everything up to here assumed one vendor running everything. This chapter covers the two ways to bring another AI into the picture — a foreign-LLM specialist agent, or a per-agent routing rule — and how fallback keeps a chain of them running when one is unavailable.
§ 15.1 · Harness vs. agent model
two different knobs

These are separate decisions, and mixing them up is the most common confusion here:

  • The harness is what runs the orchestrator — Claude Code, OpenCode (Experimental), or Codex (Experimental) (Chapter 03). Changing it changes who coordinates the whole session.
  • The agent model is what a specialist agent runs on underneath — it can differ per agent, and per agent from the harness itself. A Claude Code session can delegate one task to a Claude-native specialist and another to a Gemini- or Grok-backed one, without ever leaving Claude Code as the harness.

A foreign-LLM specialist still reports back through the same delegation contract every agent uses — the orchestrator dispatches it, it does the work, it reports a structured result — so it shows up in Metrics and Delegation exactly like any other agent, just with a different vendor label.

§ 15.2 · Option 1 · the Multi-LLM agents pack
ready-made foreign-LLM specialists

The optional Multi-LLM agents pack (Packs view, id multi-llm) adds five agents that each reach a different backend through an MCP bridge. Install the matching MCP server first — the pack itself has no single MCP dependency, so the panel won't show a needs-MCP badge to remind you.

Every agent in the pack reviews or implements and returns a structured, machine-parseable verdict — never free-form prose — and treats an unreachable/quota-exhausted provider as provider-unavailable, never a silent pass. Each is a single-pass worker: it doesn't loop or self-review.

Codex and Claude Worker are subscription-backed

These two don't use a metered API key at all — they shell out to the vendor's own official CLI (codex, claude) that you're already logged into, so a subscription seat (ChatGPT Plus/Pro, Claude Max/Pro) can do delegated work without TycoonAgents ever touching a credential. This only activates when an agent's own configuration names that MCP server — nothing routes to a subscription CLI implicitly.

OpenCode (Experimental): Claude models there default to an Anthropic API key (ANTHROPIC_API_KEY, metered). Using Claude Worker or any Claude slot through the claude CLI is an explicit opt-in: turn on Allow Claude subscription via the claude CLI under OpenCode in Settings (off by default). Existing setups that already use it keep working and show this note: “Uses your own Claude Code CLI login. Anthropic's terms for third-party harnesses have changed several times; check them before relying on this.” Claude Code and Codex are unaffected.

See docs/adding-a-non-anthropic-agent.md and docs/AGENT-BACKENDS.md for the full wiring, including the .mcp.json.example entries to copy.

Setting provider keys

Each provider looks for its key under a fixed name. You give TycoonAgents the name; the value stays on your machine.

ProviderWhat it needs
MistralMISTRAL_API_KEY (optional MISTRAL_BASE_URL)
xAI GrokXAI_API_KEY (optional XAI_BASE_URL)
Kimi (Moonshot)MOONSHOT_API_KEY (optional MOONSHOT_BASE_URL, default https://api.moonshot.ai/v1)
Local models (Qwen3 via Ollama or LM Studio)OPENAI_COMPAT_BASE_URL (e.g. http://localhost:11434/v1) and optionally OPENAI_COMPAT_API_KEY
Gemini via Antigravityno key — uses your Antigravity sign-in. GEMINI_API_KEY is only for the paid gemini backend.
Codex, Claude Workerno key — they use your own CLI sign-ins (codex login, claude)

Option A — in the panel (easiest).

  1. Open Routing and pick the agent.
  2. On Claude Code and Codex, each provider shows fixed key rows: the variable name is already filled in (e.g. MISTRAL_API_KEY) and the row shows whether it is set or unset. On OpenCode, and for Custom endpoint…, you type the names yourself in the API key env / Endpoint URL env fields.
  3. Click Set value…, paste the key, and press Save. Clear stored value removes it again.
  4. Click Test connection to make one tiny real call. The key is only ever sent over https to that provider's own host. If you set a custom base URL, the result says so and nothing is tested automatically.

The value is stored for your user only, never in the project, and takes effect without restarting.

Option B — a Windows user variable.

  1. Press Start and type environment, then open Edit environment variables for your account.
  2. Under User variables, click New…, enter the name and the value, and click OK.
  3. Fully quit and reopen VS Code. A window reload is not enough.

On macOS or Linux, add export NAME=value to your shell profile, then restart VS Code.

Never paste a key into chat or commit it. .mcp.json only ever holds names.

Gemini backend. The Gemini agent has a Gemini backend select: Antigravity sign-in or Paid key (Gemini CLI). It writes GEMINI_MCP_BACKEND into the gemini server entry in .mcp.json and nothing else. On Antigravity the model is read-only (“Gemini 3.5 Flash — set by Antigravity”) and no key is needed. After switching, reload MCP servers (/mcp or Reload Window).

Set outside the panel. A collapsed box on the Agents screen lists bridge timeouts and Codex backend settings that change behaviour but live in .mcp.json or your environment. Each shows its value and source (default, environment or .mcp.json) and is read-only; edit it where it lives, then reload MCP servers.

Fallback chains by host. A note above the chain says what your host supports: Claude Code gets full fallback (dispatcher plus hook), OpenCode is best-effort (it only switches the model string), and Codex only follows vendors with a dispatcher adapter. Google fallbacks are skipped on Codex, and the chain moves to the next entry.

§ 15.3 · Option 2 · the Routing view
any OpenAI-compatible endpoint

The Routing view (Chapter 03, § 3.8) is the other path in, and it doesn't require the Multi-LLM agents pack at all. Its Custom endpoint… vendor option targets any OpenAI-compatible server — Grok, Kimi, Qwen, or a model you're hosting yourself:

  1. Open Routing from the panel menu and pick an agent row.
  2. Choose Custom endpoint… as the vendor. Give it a Provider name (e.g. ollama-windows), the exact Model id your endpoint serves, and a Billing label (metered, subscription, or local).
  3. Set Endpoint URL env and API key env to environment variable names only, then click Set value… next to each to store the actual URL/key — both are saved under the TycoonAgents per-user app-data folder, never in the project. The field only ever shows a "stored locally" dot, never the value itself.
  4. Save writes the slot to routing.json.

Pick this option when you don't need a specialist's own review-verdict contract and just want an agent that already exists in your roster to run on a different model.

Use any OpenAI-compatible model

Most model servers and hosts speak the same OpenAI-style chat API — local ones like Ollama, LM Studio, vLLM and the llama.cpp server, and hosted ones like OpenRouter, Groq, Together, DeepSeek and Fireworks. That means a brand-new model usually works the day it appears, with no TycoonAgents update.

  1. Open Routing, pick the agent, and set Vendor to Custom endpoint….
  2. Fill in Base URL variable with a variable name that ends in _BASE_URL, for example OLLAMA_BASE_URL. Its value is the server's address, such as http://localhost:11434/v1 for Ollama.
  3. Fill in API key variable — optional for local servers with a name that looks like an API key, ending in _API_KEY, _KEY or _TOKEN (for example GROQ_API_KEY). It can't be another service's credential, such as GITHUB_TOKEN; the panel shows a warning if it is. Leave it empty for a local server that needs no key.
  4. Click Set value… beside each variable to store its value in your own settings. Each field shows whether the variable is set or unset.
  5. Pick the model with Custom… and type its exact name, as the server lists it.
  6. Click Test connection to confirm it answers.

The URL and key values must come from your own settings (Set value…) or your environment — never from files in the project. Plain http is accepted only for your own machine (localhost); anything remote needs https. Give each custom endpoint its own variable names, so you can set up several side by side, one per agent or fallback slot.

You still need a TycoonAgents update for tools that use their own sign-in (Codex, Antigravity, the Claude CLI) and for vendors without an OpenAI-style API.

§ 15.4· Copy-paste prompts
create a foreign-backed subagent from scratch

These prompts ask your current harness to add a brand-new agent backed by another AI. All of them name environment variable names only — never a value. Set the actual key yourself first, either with setx VAR_NAME "value" (Windows) or your shell profile's export VAR_NAME=value (macOS/Linux), or through the panel's Routing view Set value… button.

Prefer a subagent in your current harness

Adding a foreign-backed subagent to your current harness (below) keeps it inside TycoonAgents' delegation tracking, Metrics/Delegation tabs, and fallback chains. Configuring the other tool directly instead — running Gemini's own CLI by hand, say — works, but that work won't show up on stage, in Metrics, or in a fallback chain at all. Reach for a subagent unless you specifically need to work outside TycoonAgents entirely.

`backend.model` field.

Codex (Experimental) — new agent, as far as it's supported

Using AGENTS.md (or whatever agent mechanism this Codex CLI version
actually supports), describe a specialist role for <task> that should
run on <vendor> instead of the default model.

Codex's agent story is narrower than Claude Code's or OpenCode's subagent
files today — check what this repo's AGENTS.md and Codex CLI version
actually support before assuming per-agent backend routing exists here.
If per-agent MCP backends aren't supported, describe the role and note
that as a limitation rather than inventing a mechanism that doesn't exist.

Reference env var names only, never a value.
§ 15.5 · Fallback and default fallback
what happens when a provider fails

Every agent in the Routing view can carry an ordered fallback chain (up to 3 deep) plus an optional default fallback that applies once that chain runs out, or immediately if the agent has none.

Trigger conditions: a fallback fires on quota/usage-limit exhaustion, a 401/429 response, or a connection failure (endpoint unreachable, missing). The agent's own chain is tried first, in order; the default fallback fires only after that chain is exhausted. It never falls back to itself and never repeats an agent already tried.

Worked example

{
  "agents": {
    "kimi-reviewer": {
      "vendor": "moonshot",
      "model": "moonshot/kimi-k2",
      "costModelClass": "metered",
      "endpointEnv": "OPENAI_COMPAT_BASE_URL",
      "apiKeyEnv": "OPENAI_COMPAT_API_KEY",
      "fallback": [
        {
          "vendor": "openai",
          "model": "openai/gpt-5.6-sol",
          "costModelClass": "subscription",
          "mcpServer": "codex"
        }
      ],
      "useDefaultFallback": true
    }
  },
  "defaultFallback": {
    "vendor": "anthropic",
    "model": "anthropic/sonnet",
    "costModelClass": "metered"
  }
}

Here, kimi-reviewer runs on Kimi first; if that's unreachable, it tries the Codex reviewer next; if that also fails (and useDefaultFallback is checked, as it is by default), it finally falls back to the project's default — here, a plain Claude Sonnet run. The sonnet alias always resolves to the newest Sonnet; write a specific model id there only if you want to pin it.

How it shows in the panel

  • A fallback entry is labeled " (fb)", and the default fallback specifically is labeled " (dfb)" — both render amber.
  • Each agent's "Fallback chain (N)" section shows the default fallback as a final amber (fb) row with a "Use default fallback for this agent" checkbox, checked by default; unchecking it makes that agent fail after its own chain instead of reaching the default.
  • An agent row that actually ran on a fallback entry carries a "ran on fallback" chip.
  • Light blue marks a foreign LLM in the Metrics view specifically, and only while it's actively running — it's not a stage ring or a permanent label.
Troubleshooting

An agent whose MCP server isn't set up can't be routed to at all — a fallback target has to be dispatchable in the current harness, and the Routing view flags one that isn't with an amber warning. If a fallback never seems to fire, confirm the target agent's own MCP server (Gemini, the openai-compatible bridge, Codex) is actually configured and reachable before assuming the chain itself is broken.

See docs/ROUTING-PROFILE.md for the full schema and the README's Default fallback section for the complete trigger list.

§ 15.6 · Which option should I pick?
quick reference
SituationPick
Want a ready-made reviewer/worker on Codex, Gemini, Kimi, Grok, Mistral, or a Claude subscription seatMulti-LLM agents pack (§ 15.2)
Want an existing agent to run on a different model, no new verdict contract neededRouting view · Custom endpoint… (§ 15.3)
Want a brand-new specialist role backed by a vendor not covered by the packCopy-paste prompt in your harness (§ 15.4)
