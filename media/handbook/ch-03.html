03

Standalone and OpenCode Setup

Same product, three fronts
TycoonAgents is one scene renderer that can watch three different combinations of editor and coding-agent harness. Only how you set it up differs — once the panel is open, every feature in the rest of this handbook (Theme Maker, Metrics, Delegation, Project Plan) behaves identically no matter which front you're on. If you installed via VS Code + Claude Code in Chapter 02, you can skip straight to Chapter 04.
§ 3.1 · Requirements
by setup
SetupRequires
All three Node.js 18+ on PATH (the standalone host and the OpenCode config generator both run on it; CI runs Node 20).
Any OpenCode front OpenCode 1.18.x with at least one provider configured — OpenCode Zen's free models work for a first look, no card required.
Subscription-backed agents (Claude Code, Codex) The vendor's own CLI installed and logged in (the Claude Code CLI, the Codex CLI). TycoonAgents never sees or handles credentials — it shells out to the CLI you've already authenticated, and only ever reads back its own environment-variable names.
§ 3.2 · Setup A · VS Code + Claude Code
the default

This is the path Chapter 02 walks through in full — install the extension, let the first-run wizard configure hooks and the agent roster, done.

§ 3.3 · Setup B · Standalone + Claude Code
no VS Code required

The standalone host watches the same .claude/tycoon/ activity data the VS Code extension watches and serves the identical, unmodified panel in a browser tab instead. From the repo root: 

node standalone/src/cli.mjs install-hook .
node standalone/src/cli.mjs watch .

install-hook registers the Claude Code hook in the target project (idempotent — safe to re-run); watch starts the server and opens the panel in your default browser. Full flags, multi-directory watching, and the underlying architecture are in standalone/README.md.

§ 3.4 · Setup C · Standalone + OpenCode
a different harness entirely

Swap the coding-agent harness itself: OpenCode's plugin hooks feed the same normalized event stream the Claude Code hook produces, so the panel can't tell the difference. From the repo root: 

npm run build
npm run opencode:config
node standalone/src/cli.mjs install-hook . --opencode
node standalone/src/cli.mjs watch . --provider opencode

npm run build compiles the shared state logic the standalone requires at runtime (see the note in standalone/README.md on why it isn't reimplemented); opencode:config generates the OpenCode-side plugin registration. If you'd rather run OpenCode inside VS Code, set tycoonagents.provider to "opencode" in Settings (Chapter 10) instead — or the TYCOON_PROVIDER environment variable, which always overrides the setting. The full hook contract and event mapping are in docs/OPENCODE-PROVIDER.md.

Note

An optional "Multi-LLM agents" pack lets specialist agents run on Codex, Gemini, Kimi, or any OpenAI-compatible endpoint instead of Claude, declared per-agent rather than hardcoded — see docs/AGENT-BACKENDS.md. It's early: schema and parser only so far, not yet wired into the hook's dispatch path.

§ 3.5 · What differs on screen
provider, vendor, cost class

Once a provider other than the default is in play, a few things appear that a single-provider Claude Code setup never shows:

  • The active provider is shown per session.
  • Worker cards carry a vendor / model label instead of always assuming Claude.
  • The Metrics tab's pricing column groups by cost class — metered (pay-per-token API), subscription (a CLI you're already paying for), or local — since the three aren't comparable in raw dollar terms.
Token-accounting note

OpenCode's own terminal UI shows the parent session's current context size. That is not the same number the panel reports as usage: the panel's token counts come from each SubagentStop event (fresh tokens plus cache-read tokens), matching the accounting the Claude Code provider already uses. Expect the two numbers to disagree — they're measuring different things.

§ 3.6 · Not yet at parity
be aware before you rely on it

The standalone host and the VS Code extension share the exact same panel code, but a couple of things are worth knowing honestly rather than discovering the hard way:

  • A feature-by-feature parity table between the VS Code host and the standalone host doesn't exist yet — it's planned for a later phase of this project's own plan. Until then, check standalone/README.md directly for anything that touches feedback submission or the theme-view flow, since those are the areas most likely to differ.
  • The OpenCode desktop app and the OpenCode VS Code extension are both unverified fronts for this integration — only the OpenCode terminal TUI has been smoke-tested end to end (see docs/OPENCODE-PROVIDER.md). They may work; they simply haven't been checked.

None of this affects Setup A or Setup B — it's specific to running OpenCode as the harness.

§ 3.7 · Routing: choosing models per agent
the Routing view

Once a front is running, the Routing view lets you send different agents to different vendors, models, or local endpoints without editing files by hand.

  1. In Settings, use “Which tool runs your agents?” to pick the harness (Claude Code or OpenCode).
  2. Open the Routing view from the panel menu.
  3. Fill in the orchestrator slot at the top the same way as any agent row below.
  4. For a per-agent model, pick Vendor then choose a preset from the Model dropdown.
  5. For a local or VM-hosted OpenAI-compatible server, pick Custom endpoint… as the vendor: give it a Provider name (e.g. ollama-windows), the Model id exactly as your endpoint serves it, and Cost class local. Set the Endpoint URL env and API key env fields to environment variable names only, then click Set value… next to each to store the actual URL/key — both are saved under the TycoonAgents per-user app-data folder, never in the project, and each shows a dot reading “stored locally” once set. Clear stored value removes one.
  6. Expand “Fallback chain (N)” and “+ Add fallback” to add ordered fallback slots (e.g. opencode/big-pickle, then a subscription-backed slot).
  7. Save writes the resolved slots to routing.json, applies managed backend: blocks to agent files, and adds a secret-free provider entry to opencode.json plus your user-level OpenCode config (file references only) — any slot about to change shows a “will be written to routing.json” marker first.
  8. Clear profile removes the routing profile and its generated blocks but keeps everything you stored via Set value….
  9. Each agent row shows its “model from …” source line, a “ran on fallback” chip when it last ran on a fallback entry, and the view's Totals block rolls up per-vendor and per-cost-class counts.

See docs/ROUTING-PROFILE.md for the full routing.json schema.
